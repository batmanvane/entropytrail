# Outcomes, Forks and Analysis Implementation Plan (Plan 2: WP4, WP5, WP6)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the 420 recorded apps into an outcome table (render status, screenshots, embeddings, fingerprints), run the fork experiments that measure how much a high-entropy choice changes the outcome, and test H1–H5 as fixed in the frozen analysis plan.

**Architecture:** Three parts on one package. Part A (WP4) adds a token section classifier and a resumable `et eval` pipeline that writes an `eval/` folder into every unit directory (an app or a fork rollout): headless Chromium render with a fixed interaction, two screenshots, image and code embeddings, structural fingerprint. A single `outcome_distance` built on those is the yardstick for ensemble spread (H2) and fork importance (H3). Part B (WP5) selects fork sites from the recorded tokens, forces alternatives with the existing recorder, stores each rollout as a normal unit directory under the parent app, and runs in the existing night window. Part C (WP6) computes per-app landscape measures and the five primary tests, writing small committed tables and figures under `results/`.

**Tech Stack:** Python 3.12 via uv; existing mlx/mlx-lm 0.32.2 recorder; new dependency group `eval` (playwright, torch, transformers, sentence-transformers, pillow) and `analysis` (pandas, scipy, statsmodels, diptest, matplotlib); pytest.

**Spec:** `docs/superpowers/specs/2026-11-19-entropytrail-design.md` (§5.4, §5.5, §5.6, §5.7, §6, §8, §11 WP4–WP6) and the frozen analysis plan in `docs/METHODS.md` (D-028, D-029). Executors read both.

**Not in this plan:** website and human ratings (WP7), hidden-state trajectories (D3), the scale-up of forks beyond the pilot (decided by Robert after Task B5, D2), temperature sweep (WP12).

## Global Constraints

- Condition `qwen35-9b-bf16-mlx-1195d88b`, data root `/Volumes/Data/entropytrail` (env `ENTROPYTRAIL_DATA`), prompt set v1, 21 prompts × 20 samples. Raw data never goes into the repo; `results/` holds only small derived tables and figures.
- Fork rollouts are generated by the same recorder, same condition, same machine (Mac Studio), temperature 1.0, no truncation, total length cap 16,000 tokens counted from the start of the app's generation (spec §8, D-010).
- Frozen definitions (METHODS.md): fork = **code** token with H ≥ 2 bits; comment token = token whose **first character** lies in a JS/CSS `//…`, `/*…*/` or HTML `<!--…-->` comment, ignoring markers inside string literals; only the app part (extracted HTML span) counts; thresholds 2 bits, 4 bits, last third are fixed.
- Fork sites (spec §5.4): N = 10 top-H code tokens + 3 random code tokens per app; top-3 alternatives ≠ actual token, 1 rollout each; 2 same-token rollouts (baseline).
- Fork importance = mean outcome distance alt-vs-same − mean distance same-vs-same.
- Mixed models with prompt as random effect, domain and openness fixed; Holm across the five primary tests, α = 0.05; one-sided where the plan says so. H4/H5 primary outcomes are **human** ratings; Claude ratings (D-030) are a separate outcome and never pooled.
- Every builder choice gets a `docs/DECISIONS.md` entry; every run gets a `docs/JOURNAL.md` entry; every new file/key goes into `docs/DATA.md`.
- `et generate` / `et run-window` refuse a dirty tree; the night run uses `uv run --frozen --offline`, so `uv.lock` must be committed before any night that needs new code.
- Public repo: commit trailer only `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; no claude.ai links.
- Tests: fast tests run by default; tests that need the 9B weights, the embedding models or a real browser are marked `slow` (models) or `browser` (Chromium; add the marker to `pyproject.toml`).

## Review Focus

1. **Apps that hang or never finish loading** (infinite loops, `while(true)`, huge canvases): render must time out per page, record `timeout: true`, `renders: false`, and continue with the next unit — test in A2.
2. **Units without `app.html`** (no HTML extracted, or a rollout forced into EOS early): eval must still write a complete `eval/` with `renders: false` and blank-page screenshots so every unit has an outcome; outcome distance to a rendering app is 1.0 — tests in A2, A4.
3. **Comment markers inside strings, URLs and regex-free JS** (`"http://x"`, `'/* not */'`, template literals): must not create comment tokens — tests in A1.
4. **Night interruption in the middle of a fork** (5 rollouts, deadline after 2): the 2 finished rollouts stay, the interrupted one is discarded, the next night continues with rollout 3 — test in B2.
5. **Forks whose alternatives include EOS or whose position is near the 16k cap**: forced EOS yields an empty continuation (app = prefix), budget ≤ 0 yields no generation; neither crashes — test in B2.

**Interfaces:**
- Produces: `app_span(output: str) -> tuple[int, int] | None` — char span of `extract_html(output)` inside `output` (`output.find(html)`; None if no HTML).
- Produces: `char_sections(html: str) -> list[str]` — one label per char of `html`, from `{"html", "css", "js", "text", "comment"}`.
- Produces: `token_sections(output: str, char_offsets: list[int], *, detail: bool = False) -> list[str]` — label of each token's first char; tokens whose first char is outside `app_span` (or with no app) get `"outside"`; a token starting at `len(output)` (EOS) gets `"outside"`. With `detail=True` comments are split into `"js-comment"`, `"css-comment"`, `"html-comment"` (needed for late JS surprise in C1); `char_sections` takes the same `detail` flag.
- Produces: `CODE_SECTIONS = frozenset({"html", "css", "js", "text"})`.

Rules: inside `<style>…</style>` content is `css`, `/*…*/` there is `comment`; inside `<script>…</script>` content is `js`, `//…` to end of line and `/*…*/` are `comment`, with `'…'`, `"…"` and `` `…` `` string scanning (backslash escapes) so markers inside strings are code; `<!--…-->` outside script/style is `comment`; characters inside `<…>` tags (including `<script>` / `<style>` tags themselves) are `html`; other characters are `text`. Regex literals are not detected (documented limitation).

**Interfaces:**
- Produces: `render_app(html: str | None, out_dir: Path, *, browser, timeout_s: float = 15.0) -> dict`. Writes `out_dir/load.png` and `out_dir/interact.png` (always; a blank page when `html is None` or on timeout) and returns the render record (also written as `out_dir/render.json`):
  `{"renders": bool, "timeout": bool, "n_page_errors": int, "n_console_errors": int, "page_errors": [str, ≤20], "console_errors": [str, ≤20], "n_page_errors_after_interaction": int, "body_text_chars": int, "viewport": [1024, 768], "random_seed": 12345, "playwright": str, "chromium": str}`.
- Produces: `RENDER_VERSION = 1` (bump if the procedure changes).

Procedure (fixed for apps and rollouts, so screens are comparable):
1. New browser context per call (isolated storage), viewport 1024×768, device scale 1. Init script replaces `Math.random` by mulberry32 seeded with 12345 and `alert/confirm/prompt` by console logging (copy the shim from `scripts/serve_apps.py`). All requests except the app's own `file://` URL are aborted (no network).
2. Write the HTML to a temp file, `goto` it (`wait_until="load"`, timeout `timeout_s`), wait 1500 ms, screenshot `load.png`. `renders` = page loaded and `n_page_errors == 0` at this point and `html is not None`.
3. Interaction: click the first visible `button` (else the centre of the first `canvas`, else nothing); press `ArrowRight`, `ArrowUp`, `Space`, `Enter` 150 ms apart; type `42` into the first visible `input[type=number], input[type=text], input:not([type])` if present; wait 1000 ms; screenshot `interact.png`.
4. Every step is guarded: a timeout or crash sets `timeout: true` (if the page did not finish), keeps counters so far, writes a blank 1024×768 PNG for missing screenshots, and closes the context. A hung page must not block more than ~`timeout_s + 10` s.
